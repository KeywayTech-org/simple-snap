# 0002 — 三阶段进度展示

- 状态: 接受
- 日期: 2025-09-03
- 范围: Demo v1

## 背景

链路有三个时延环节：上传源照片、LLM 读图写 prompt、GPT-image 生成图。每段 5–20s，总耗时可能 30–60s。单一 loading 转圈会让用户怀疑页面卡死。

## 决策

采用 **3 阶段进度条**，每段独立 label，独立状态：

```
[1] 上传中…
[2] AI 解读中…
[3] 正在创作…
```

后端提供同步 `POST /api/poster` 接口，由前端在前端控制阶段切换。**不上 WebSocket、不上 Server-Sent Events**。

## 后果

- **正**:
  - 1 秒级轮询代价几乎为 0（仅切换 label，不需要真实进度）。
  - 用户能精确定位失败发生在哪一段，错误 Toast 可以指明"第 X 步超时，请重试"。
  - 实现简单：前端用 1 个 `setInterval` 或 `await` 链即可。
- **负**:
  - "AI 解读中"和"正在创作"在前端看是黑盒，**前端的进度是名义进度，不是真实进度**——用户可能被"假进度"误导。
  - 同步接口意味着前端要等 GPT-image 跑完才能拿到结果，最长 60s 内 HTTP 连接可能超时（需后端设置长连接或异步轮询）。
- **可逆性**: 高。后续可平滑升级到 SSE 或 WebSocket，不影响 PRD 用户故事。

## 备选

- **WebSocket 推送真实进度**: GPT-image 本身不提供进度事件，需要后端伪造事件流，工程量翻倍但收益小。
- **单 loading + 模糊文案**: 实施最简，UX 较差，已被否决。

## 升级路径

如果用户反馈"假进度不可信"或真实后端时延超过 60s → 升级到 SSE，引入 `/api/poster/jobs/:id` 异步任务接口。
