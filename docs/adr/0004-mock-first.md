# 0004 — Mock 后端 + 流程界面优先

- 状态: 接受
- 日期: 2025-09-03
- 范围: Demo v1

## 背景

原计划 Demo v1 已包含"后端单接口"（ADR-0001）。但实际推进中，确认**先做前端 + Mock**，理由：

1. **核心价值是流程展示**：Demo 的目标读者（老板/PM/早期用户）想看的是"上传 → 进度 → 出图 → 重做"这条链跑得顺不顺。
2. **后端是真链路里最重的环节**：LLM 调用 + GPT-image 一次跑 30-60s + 拒生处理 + 失败重试。这些在 demo 阶段会喧宾夺主。
3. **前端设计是会被反复修改的部分**：先用 mock 把界面/动效打磨到"上线级"，再接真接口时基本不动 UI。

## 决策

**Demo v1 拆为两阶段**：

- **阶段 A（本次 PRD 范围）**：
  - 仅前端 + Mock 后端（返回固定 mock 数据）
  - 三阶段进度条**用 setTimeout 模拟**：上传 1s → 解读 2s → 创作 4s，总 7s
  - 5 张预置 mock 作品图（按高纯度色区分）
  - 重点：UI 视觉、动效、交互细节
- **阶段 B（接真接口）**：
  - 接 LLM API（multimodal）
  - 接 GPT-image API
  - 替换 mock 进度为真实进度
  - 接入 ADR-0001 描述的真实链路

## 后果

- **正**:
  - 7s 完成一次"假创作"，可短时间内多次试错 UI。
  - 界面/动效/文案可以**完全打磨到上线级**再接 API。
  - Demo 展示时不需要消耗 API 预算。
  - 移动端、桌面端、暗色/亮色都可以独立调。
- **负**:
  - 阶段 A 看到的进度是"假的"，但**对 demo 来说反而是优点**（快）。
  - 阶段 A 拒生处理是 mock 的"假拒生"，阶段 B 才会暴露真实拒生体验。
  - 阶段 A 的 prompt 模板不实际运行，阶段 B 需要重新验证 PRD §6 验收标准。
- **可逆性**: 高。阶段 B 仅替换 fetch 入口，不影响 UI 组件树。

## 升级路径

阶段 B 触发条件：

- [ ] 阶段 A UI/动效通过内部评审
- [ ] 阶段 A PRD §6 验收标准的人工核对全部通过
- [ ] API 预算与配额确定

升级时只动 `src/api/poster.ts` 一个文件，UI 不变。
